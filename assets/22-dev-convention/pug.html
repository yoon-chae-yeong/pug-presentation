AI PUG Dev Convention Guide

개발 업무에서 '컨벤션(Convention)'이란 무엇인가요?

컨벤션은 직역하면 '관습', '약속'입니다. 개발 업무에서의 컨벤션은 여러 명이 함께 코드를 짤 때 코드가 한 사람이 짠 것처럼 보이도록 미리 정해둔 협업의 교통법규와 같습니다.

🚦

왜 약속이 필요할까요?

도로 위에 신호등이 없다면 사고가 나듯, 프로젝트에서도 각자 원하는 스타일대로 파일명을 짓고 커밋을 올리면 코드가 뒤엉키고 소통 오버헤드가 폭발하게 됩니다.

🤝

비개발자에게 왜 중요할까요?

마케터, 기획자, 데이터 분석가 등 협업하는 모든 주체가 같은 규칙으로 파일을 관리하고 깃을 사용해야 불필요한 인수인계 비용을 아끼고 결과물을 안정적으로 배포할 수 있습니다.

⚡

규칙이 가져다주는 결과

파일명만 보고도 무엇을 하는 파일인지, 오늘 올라온 커밋 메시지만 보고도 어떤 기능을 수정했는지 1초 만에 알 수 있게 되어 개발 가속도가 극대화됩니다.

주요 프로그래밍 네이밍 표기법

코딩할 때 변수, 함수, 파일 이름 등을 지을 때 띄어쓰기를 표현하는 대표적인 4가지 케이스를 알아봅니다.

케밥 케이스
(kebab-case)
ai-pug-project

단어와 단어 사이를 하이픈(-)으로 연결하는 방식입니다. 꼬치(케밥)에 꽂힌 고기 같다고 해서 붙여진 이름입니다. 웹 URL 경로 및 프로젝트 디렉토리명에 널리 쓰입니다.

카멜 케이스
(camelCase)
aiPugProject

첫 단어는 소문자, 그 다음 단어의 첫 글자는 대문자로 표기하여 낙타(camel)의 등처럼 솟아오르게 하는 표기법입니다. 자바스크립트 변수 및 함수명에 쓰입니다.

파스칼 케이스
(PascalCase)
AiPugProject

모든 단어의 첫 글자를 대문자로 표기하는 방식입니다. 카멜 케이스의 확장형입니다. 주로 클래스명이나 컴포넌트(Component) 이름에 쓰입니다.

스네이크 케이스
(snake_case)
ai_pug_project

단어 사이를 언더바(_)로 연결하여 뱀(snake)이 기어가는 형태처럼 표현하는 기법입니다. 데이터베이스 테이블이나 Python 변수명에 자주 쓰입니다.

마크다운(Markdown) 문서 파일명 규칙

마크다운(.md) 문서는 프로젝트 구조에서 파일이 위치하는 깊이에 따라 다른 네이밍 규칙을 갖습니다.

1. 루트(Root) 폴더 위치 대문자 스네이크/케밥

저장소 최상위 루트 디렉토리의 핵심 기본 문서들은 모두 대문자로 네이밍합니다.

📂 Root/
  📄 README.md
  📄 CONTRIBUTING.md
  📄 DESIGN.md
2. docs 폴더 및 하위 위치 소문자 케밥 & 띄어쓰기 금지

설명서 등 상세 문서를 모아두는 docs/ 디렉토리 하위의 파일은 전부 소문자 케밥 케이스로 통일하고 공백을 금지합니다.

📂 docs/
  📄 user-manual.md
  📄 getting-started.md
  📄 api-reference.md

⚠️ 주의사항

윈도우 OS는 대소문자를 구분하지 않지만, 배포용 리눅스 서버나 Github 환경은 대소문자를 엄밀히 구분합니다. 따라서 Docs/User Manual.md처럼 대문자와 공백이 들어간 파일명은 웹상에서 경로 링크가 깨지는 원인이 되므로, docs 폴더 하위에서는 무조건 소문자와 하이픈(-)만 사용해야 합니다.

Git Commit Prefix 규칙

협업 시 변경 이력을 한눈에 파악하기 위해, 커밋 제목 앞에 작업 성격을 알리는 영어 Prefix를 꼭 붙입니다.

feat
기능 개발 새로운 기능 추가
fix
버그 수정 오류나 버그 현상 해결
docs
문서 작업 문서 추가, 수정 및 보완
style
스타일 수정 코드 동작에 영향 없는 포맷팅, 세미콜론 누락 등 수정
refactor
리팩토링 기능 변경 없이 코드 구조 가독성 개선
test
테스트 코드 테스트 추가 및 리팩토링
chore
기타 빌드 설정 빌드 환경 설정 변경, 패키지 의존성 관리 등 변경
생성된 Git 커밋 명령어
git commit -m "feat: 작업 내용 요약"

좋은 Git 커밋 습관의 중요성

비개발자가 현업에서 자주 놓치는 깃 커밋 단위와 중요 습관을 짚어봅니다.

작은 단위로 자주 커밋하세요 (Atomic Commit) 하나의 커밋에는 딱 하나의 변경 사항만 기록하는 것이 좋습니다. 예를 들어 메인 레이아웃 수정과 로그인 버그 수정을 동시에 한 뒤, 통째로 커밋하는 것은 좋지 않습니다. 쪼개서 자주 기록해야 나중에 오류가 났을 때 원인을 쉽게 찾고 롤백할 수 있습니다.
모호한 커밋 메시지는 피하세요 귀찮다고 git commit -m "fix: update" 또는 git commit -m "style: 수정" 같은 성의 없는 메시지는 나중에 동료가 히스토리를 파악하는 것을 가로막습니다. 구체적으로 무엇을 해결했는지 간략히 작성하는 습관이 중요합니다.
커밋 메시지 제목은 영어 Prefix 뒤에 콜론(:)과 공백을 둡니다 표준적인 컨벤션은 feat: add login button 와 같이 콜론 뒤에 반드시 띄어쓰기를 한 칸 주는 규칙입니다. 이러한 미세한 규칙도 자동화 분석 툴 등이 커밋을 정상 파악하기 위해 필수적입니다.

모노레포(Monorepo) 구조와 작업 규칙

모노레포란? 하나의 저장소(Repository) 안에서 여러 개의 독립적인 프로젝트(예: frontend, backend)를 함께 관리하는 구조입니다.
* 💡 멀티 레포(Multi-repo): 서비스마다 독립된 깃 저장소를 따로 개설해 독립적으로 관리하는 대조 방식입니다.

🤖 AI 협업 & 바이브코딩(Vibe Coding)에서 유용한 이유

  • 단일 AI 컨텍스트: 프론트와 백엔드 코드를 AI에게 한 번에 전달하여 API 및 데이터 모델 싱크의 정확도를 높입니다.
  • 빠른 개발 흐름(Vibe) 유지: 저장소를 오가는 번거로움 없이 하나의 공간에서 수정과 검증을 동시에 처리해 고속 반복 개발을 돕습니다.
  • 타입 공유 및 오류 예방: 공통 데이터 스펙(TypeScript Types)을 직접 참조하므로, 연동 규격이 어긋나는 실수를 차단합니다.

AI PUG 프로젝트에서 모노레포 구조로 협업 시, 프로젝트 루트 위치에서 프론트엔드(화면)와 백엔드(서버/API) 디렉토리를 물리적으로 완벽히 구분하여 개발 및 관리해야 합니다.

package.json
frontend/# 프론트엔드 웹 화면 (React, Vue, HTML 등)
src/
package.json
