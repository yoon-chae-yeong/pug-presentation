1. AI 에이전트란?

AI 에이전트는 단순히 질문에 답하는 챗봇이 아니라,
목표를 이해하고 → 필요한 도구를 선택하고 → 실행하고 → 결과를 판단하고 → 최종 응답을 만드는 시스템이다.

사용자 요청
↓
Agent 판단
↓
Tool 선택
↓
API / DB / 파일 / 검색 실행
↓
결과 해석
↓
최종 답변

2. LLM과 Agent의 차이

구분 LLM Agent
역할 텍스트 생성 목표 수행
할 수 있는 일 답변, 요약, 분류 조회, 실행, 판단, 반복 수행
외부 시스템 연결 기본적으로 없음 Tool로 연결
"LLM은 두뇌이고, Agent는 두뇌 + 도구 + 실행 흐름이다."

3. Tool이란?

Tool은 에이전트가 사용할 수 있는 외부 기능이다.

  • • get_course_list()
  • • search_employee()
  • • get_inventory()
  • • create_report()
  • • send_email()
  • • query_database()
  • • call_external_api()

Tool은 에이전트의
"손과 발"이다.

OpenAI 문서에서도 function calling, tool calling은 모델이 외부 시스템과 연결되어 데이터나 기능을 사용할 수 있게 하는 방식으로 설명한다.

4. 에이전트와 Tool의 관계

"에이전트와 툴의 관계는 '직업'과 '도구 상자'의 관계와 같습니다."

1) 개발자가 툴을 '부여'합니다

에이전트를 만들 때, 우리는 그 에이전트의 목적에 맞는 툴들을 미리 손에 쥐여줍니다.

● 검색 에이전트: [구글 검색 툴, 뉴스 API 툴] 부여
● 데이터 분석 에이전트: [Python 코드 실행기, CSV 리더 툴] 부여
● 고객 응대 에이전트: [주문 조회 툴, 환불 정책 DB 툴] 부여

툴 부여 코드 예시:

@agent def research_agent(self) -> Agent: return Agent( config=self.agents_config["research_agent"], tools=[self._search_tool, self._scrape_tool], verbose=True, allow_delegation=False, )

2) '정해진 툴' 안에서 에이전트가 하는 일

툴이 정해져 있다고 해서 에이전트가 수동적인 것은 아닙니다. 에이전트의 핵심은 "어떤 툴을, 언제, 어떤 순서로 쓸지 스스로 결정한다"는 점에 있습니다.

일반 프로그램 (Non-Agent)

코딩된 순서대로 A 툴 실행 -> B 툴 실행 합니다.

에이전트 (Agent)

질문을 보고 "음, 이건 A 툴만 써도 되겠네?" 혹은 "A로 정보를 찾고, 그 결과를 바탕으로 B 툴을 써야겠다!"라고 추론(Reasoning)합니다.

3) 왜 에이전트마다 툴을 다르게 줄까요?

모든 에이전트에게 세상의 모든 툴을 다 줄 수도 있겠지만, 보통은 제한된 툴만 줍니다.

정확도 (Accuracy)

툴이 너무 많으면 에이전트가 혼란을 느껴 엉뚱한 툴을 선택할 확률(Hallucination)이 높아집니다.

비용/속도 (Efficiency)

불필요한 고민 시간을 줄이고, 꼭 필요한 작업만 빠르게 수행하기 위해서입니다.

보안 (Security)

데이터 분석 에이전트가 굳이 고객의 개인정보 수정 툴을 가질 필요는 없기 때문입니다.

5. Task: 에이전트가 수행할 구체적인 업무

에이전트가 '누구(Who)'라면, 태스크(Task)는 그 에이전트가 실제로 달성해야 할 '일(What)'입니다. 잘 정의된 태스크는 에이전트에게 명확한 가이드라인과 결과물의 형식을 제공합니다.

Agent vs Task 관계

Agent (Who)

특정한 전문성을 가진 페르소나 (예: 시장 분석 전문가)

Task (What)

에이전트가 수행해야 할 구체적인 미션 (예: 경쟁사 가격 조사)

Task 정의 코드 예시:

@task def research_task(self) -> Task: return Task( config=self.tasks_config["research_task"], ) @task def opportunity_task(self) -> Task: return Task( config=self.tasks_config["opportunity_task"], context=[self.research_task()], )

※ 하나의 에이전트는 여러 개의 태스크를 순차적으로 혹은 병렬로 수행할 수 있습니다.

6. Tool Calling이란?

Tool Calling은 LLM이 코드를 직접 실행하는 것이 아니라, "어떤 툴을 어떤 인자로 호출할지"를 구조화해 요청하는 방식이다.

사용자 입력 (터미널):

"제품 단면 품질검사 비전 AI 솔루션 시장"

코드에서 실행 시작:

crew.kickoff(inputs={"topic": user_topic})

LLM 판단 (구조화된 툴 호출 명령):

{ "tool_name": "search_the_internet_with_serper", "arguments": { "search_query": "제품 단면 품질검사 비전 AI 솔루션 시장 규모 성장률 주요 공급업체" } }

프레임워크/서버가 실제 툴 실행:

SerperDevTool(search_query="...")

결과 반환:

[ { "title": "시장 조사 보고서: 제품 단면 품질검사 비전 AI 솔루션 주요 공급업체 (2026)", "url": "https://example.com/report" } ]

LLM 최종 답변:

"리서치 결과를 정리한 뒤 Opportunity → Growth → Business Case → Validation 순서로 분석을 이어갑니다."

LLM은 호출 판단
Tool은 실제 실행
Crew는 흐름 연결

7. Tool Schema란?

Tool Schema는 LLM에게 "이 도구는 이렇게 쓰는 것이다"라고 알려주는 설명서다.

{ "name": "search_the_internet_with_serper", "description": "시장 조사 주제와 관련된 최신 웹 정보를 검색한다.", "parameters": { "type": "object", "properties": { "search_query": { "type": "string", "description": "검색할 시장 조사 질의문" } }, "required": ["search_query"] } }

잘 만든 Tool Schema는 에이전트 품질에 큰 영향을 준다.

❌ 나쁜 예

search_data: 데이터를 찾는다

✅ 좋은 예

SerperDevTool: 시장 조사 쿼리를 받아 최신 웹 근거를 검색한다.

8. Tool의 종류

1) 조회 Tool (정보 획득)

DB나 API에서 정보를 가져온다.

  • • 교육 목록 조회, 재고 조회
  • • 고객 정보 조회, 매출 데이터 조회

2) 실행 Tool (액션 수행)

실제 액션을 수행한다.

  • • 메일 발송, 신청 등록, 보고서 생성
  • • 캘린더 등록, 파일 저장

3) 계산 Tool (수치 연산)

LLM이 틀리기 쉬운 계산을 대신한다.

  • • 단가 계산, 수율 계산
  • • 예측값 계산, 통계 계산

4) 검색 Tool (지식 검색)

문서, 웹, 사내 지식 DB를 검색한다.

  • • 규정 검색, 매뉴얼 검색
  • • 회의록 검색, RAG 검색

9. 단일 Agent 구조

가장 기본 구조는 이렇다.

User → Main Agent → Tool → DB/API → Main Agent → Response

예: 시장 조사 에이전트

  • ✅ 웹 검색 기반 근거 수집
  • ✅ 주제별 핵심 포인트 정리
  • ✅ 출처 신뢰도 점검
  • ✅ 요약 리포트 생성

10. 다중 Agent란?

다중 에이전트는 여러 에이전트가 역할을 나눠서 일하는 구조다.

사용자 요청
↓
총괄 에이전트 (Supervisor)
검색 에이전트
분석 에이전트
작성 에이전트
검토 에이전트
↓
최종 결과

"다중 에이전트는 한 명이 모든 일을 하는 구조가 아니라,
역할을 나눠 협업하는 구조다."

11. 다중 Agent가 필요한 경우

아래 조건이면 다중 에이전트가 적합하다.

  • • 업무가 여러 단계로 나뉜다
  • • 각 단계의 전문성이 다르다
  • • 중간 검토가 필요하다
  • • 도구가 너무 많다
  • • 출력 품질 관리가 필요하다

예: 시장 조사 보고서 작성

  1. 1. 자료 수집
  2. 2. 데이터 분석
  3. 3. 요약 작성
  4. 4. 리스크 검토
  5. 5. 최종 보고서 생성

이런 업무는 단일 에이전트보다 다중 에이전트가 적합하다.

12. 다중 Agent 패턴

실무에서는 문제 유형에 따라 여러 패턴을 선택해 사용한다.

1) Supervisor Pattern

◈ 총괄 에이전트가 하위 에이전트들을 지휘한다.

Supervisor Agent
├─▶Research Agent
├─▶Analysis Agent
└─▶Writer Agent
복잡한 협업 조정
의사결정 집중
2) Sequential Pattern (강의 예제)

◈ 앞 단계의 결과를 다음 단계가 이어받아, 순서대로 완성도를 높여 가는 패턴이다.

Research Agent → Opportunity Agent → Growth Agent → Business Case Agent → Validation Agent
역할 분리
단계별 품질 점검
보고서 자동 생성
3) Debate Pattern

◈ 서로 다른 관점의 에이전트가 토론하고 검토 후 결론을 낸다.

찬성 Agent↔반대 Agent
↘검토 Agent→최종 판단 Agent
리스크 검토
의사결정 보강
4) Router Pattern

◈ 입력 유형에 따라 적절한 전문 에이전트로 라우팅한다.

Router Agent
├─▶HR Agent ├─▶Finance Agent
├─▶Sales Agent └─▶Production Agent
요청 분류
전문화 대응
5) Swarm Pattern

◈ 여러 에이전트가 자율적으로 상호작용하며 문제를 해결한다.

Agent A↔ Agent B↔ Agent C↔ Agent D
자율 협업
유연한 작업 분산

13. 에이전트 인계(Handoff) 규칙

다음 단계가 바로 활용할 수 있도록, 인계 데이터는 구조화된 형태로 넘긴다.

입력 예시

{ "topic": "제품 단면 품질검사 비전 AI 솔루션 시장", "question": "시장 기회와 핵심 공급업체를 알려줘" }

출력 예시

{ "sources": [ { "title": "시장 조사 보고서: 제품 단면 품질검사 비전 AI 솔루션 주요 공급업체 (2026)", "url": "https://example.com/report" } ] }

14. 다중 Agent에서 중요한 개념

1) Role (역할)

각 에이전트의 역할: 검색 담당, 분석 담당, 작성 담당, 검토 담당, 실행 담당. 역할이 겹치면 결과가 흐려진다.

2) Goal (목표)

❌ 나쁜 예:
"좋은 답변을 만든다"

✅ 좋은 예:
"제품 단면 품질검사 비전 AI 솔루션 시장의 최신 동향과 핵심 공급업체를 근거와 함께 3개 이상 찾는다"

3) Input / 4) Output (데이터 규격)

Input 예시:

{ "topic": "제품 단면 품질검사 비전 AI 솔루션 시장", "question": "시장 기회와 핵심 공급업체를 알려줘" }

Output 예시:

{ "sources": [ { "title": "시장 조사 보고서: 제품 단면 품질검사 비전 AI 솔루션 주요 공급업체 (2026)", "url": "https://example.com/report" } ] }

※ 다중 에이전트에서는 Output 형식을 반드시 정해야 한다.

4) Handoff (인계)

한 에이전트가 다음 에이전트에게 작업을 넘기는 것. (Research Agent → Opportunity Agent)
넘길 때는 자연어보다 구조화된 형식이 좋다.

15. AI 에이전트 프레임워크 비교

에이전트 시스템을 구축할 때 자주 비교되는 대표 프레임워크들이다.

비교 항목 LangGraph CrewAI AutoGen Assistants API
제어권 (Control) 최상 (세밀한 제어) 중 (추상화 높음) 중상 (커스터마이징 가능) 낮음 (OpenAI 의존)
복잡도 (Complexity) 높음 (학습 필요) 보통 (직관적) 보통 낮음 (매우 쉬움)
상태 관리 매우 강력 (Persistence) 보통 보통 자동 (서버에서 관리)
주요 철학 결정론적 흐름 제어 역할 기반 협업 에이전트 간 대화 편리한 도구 통합

16. CrewAI 핵심 구성요소

시장 조사 멀티에이전트 시스템을 구성할 때 꼭 이해해야 할 요소들이다.

  • • Agent (역할 정의):
    역할(role)과 목표(goal)가 분리된 담당자 정의
    @agent def research_agent(self) -> Agent: return Agent( config=self.agents_config["research_agent"], tools=[self._search_tool, self._scrape_tool], )
  • • Task (일 정의):
    각 에이전트가 수행할 작업 설명과 기대 산출물(expected_output)
    @task def research_task(self) -> Task: return Task( config=self.tasks_config["research_task"], )
  • • Crew (협업 오케스트레이터):
    여러 Agent와 Task를 하나의 실행 단위로 묶어 워크플로우를 관리
    my_crew = Crew( agents=self.agents, tasks=self.tasks, )
  • • Crew + Process (오케스트레이션):
    에이전트/태스크를 묶고 실행 방식(Sequential 등) 지정
    @crew def crew(self) -> Crew: return Crew( agents=self.agents, tasks=self.tasks, process=Process.sequential, )

17. 구현할 때 주의할 점

1) 처음부터 너무 똑똑한 에이전트를 만들지 말기

처음에는 정해진 순서대로 Agent 실행(Sequential)부터 시작하고, 그 다음 Supervisor가 조건에 따라 선택하게 확장하라.

2) Agent별 Output 형식을 명확히 정의하기

나쁜 방식: "적당히 답변해줘"

좋은 방식: "핵심 근거·수치·출처·가정을 포함한 구조화된 리서치 요약"

3) Tool은 작고 명확하게 만들기

나쁜 Tool: process_everything()

좋은 Tool: SerperDevTool(), ScrapeWebsiteTool()

4) Agent 역할을 겹치게 하지 않기

SearchAgent가 추천까지 하면 RecommendAgent가 필요 없어진다. 역할은 철저히 분리해야 한다.

5) DB에 없는 내용을 만들지 못하게 하기

프롬프트에 반드시 넣기: "수집한 출처에 없는 시장 사실/수치는 절대 생성하지 마라."
